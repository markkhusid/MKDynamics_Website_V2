A [fuzzer](https://grokipedia.com/page/Fuzzing) feeds a program inputs it did not expect and watches for a crash. Barton Miller's group did this to Unix utilities in 1988 by feeding them noise. The submission is a dumb mutational fuzzer written in C. The program never opens the target. It starts from a seed and edits that seed.

The notebook next to the source is a scratch pad. It checks the two arguments, reads a seed as raw bytes, sketches a Python generator, and looks at strings inside a target. ## What the notebook was checking

The notebook stores both arguments as 32-bit integers. The first seeds the random number generator. The second is the iteration count. It then reads a seed as bytes.

A later cell sketches a different generator. It seeds Python's `random` from the file bytes and draws an integer from 0 to 100. The function takes the command-line integer and never uses it. That sketch stayed in the notebook. In the C program the file is the specimen, and the command-line integer is the dice.

The notebook also opens a target and lists strings stored in it. A fuzzer can keep those strings as a dictionary, so some of the noise looks like a token the program already compares against. The C program never opens a target. Every new byte is a random value. The dictionary idea stayed in the notebook.

## The shape of a run

The program takes two arguments, reads a file named `seed` from the current directory, and writes one buffer to standard output. Debug prints in the submitted file are comments, so the stream can be the entire input of whatever runs next.

The same arguments and the same seed file produce the same bytes. `srand` is called once, before the loop, with the first argument. Every later `rand` call follows from that.

```c
if (argc != 3) {
    printf("Usage: ./fuzzer <prng_seed> <num_interations>\n\r");
    exit(0);
}

prng_seed = atoi(argv[1]);
num_iterations = atoi(argv[2]);
```

The usage line spells the second argument `num_interations`. The notebook spells it the same way. `atoi` parses a leading integer and returns 0 when the text has no number. A bad argument count exits with status 0. A finished run exits with status 0 as well.

## The seed is copied, then left on disk

Two arrays hold the work. Each is 65535 bytes. `read_seed_file` opens `seed` in binary mode and reads at most that many bytes. The count it returns is the length of the specimen. The function reads the file. It does not write it.

```c
int read_seed_file(char *seed_filename, char *buffer, int buffer_size)
{
    FILE *seed_file;

    seed_file = fopen(seed_filename, "rb");
    if (seed_file == NULL) {
        printf("Error opening seed file\n");
        exit(0);
    }

    int bytes_read = fread(buffer, 1, buffer_size, seed_file);
    if (bytes_read == 0 && !feof(seed_file)) {
        printf("Error reading seed file %s\n", seed_filename);
        fclose(seed_file);
        exit(0);
    }
    return bytes_read;
}
```

`main` copies the whole array, then sets the working length to the count from `fread`.

```c
char seed_buffer[65535];
char mutated_buffer[65535];

num_read_bytes = read_seed_file("seed", seed_buffer, sizeof(seed_buffer));
memcpy(mutated_buffer, seed_buffer, sizeof(seed_buffer));
mutated_buffer_size = num_read_bytes;
srand(prng_seed);
```

The rest of the program trusts that length. Bytes past it are not printed. The copy is wider than the specimen, and `fread` did not fill the tail. The append step writes its new bytes at the current length, so the printed result is the mutated specimen plus those new bytes.

Nothing checks the write against 65535. A long run appends ten bytes every 500 iterations. Past the end of the array, that store is off the end of `mutated_buffer`.

## One byte at a time, a little more than 13 percent

Each iteration walks the current specimen. For each byte it draws `rand() % 101`. A draw of 13 or less replaces that byte. The comment in the source calls the test 13 percent. `rand() % 101` has 101 outcomes, 0 through 100, and the test keeps 14 of them. The rate is 14/101.

The new value is `(rand() % 255) + 1`. The fuzzer never writes a zero of its own. A C string in the buffer is less likely to end early on a fresh zero. A zero that came in with the seed survives only while that position keeps losing the draw. A long run makes survival unlikely.

```c
void mutate_buffer(char *mutated_buffer, int mutated_buffer_size)
{
    int i;

    for (i = 0; i < mutated_buffer_size; i++) {
        if ((rand() % 101) <= 13) {
            mutated_buffer[i] = (char)((rand() % 255) + 1);
        }
    }
}
```

## Ten new bytes every 500 iterations

The loop counter starts at 1 and runs through `num_iterations` inclusive. On a multiple of 500, ten new bytes are written at the current end and the length grows by ten. The submitted test also requires the counter to be nonzero. The counter starts at 1, so that part of the test never changes a run.

A commented loop in `main` starts the counter at 499 and stops before 501. That is the author's check that iteration 500 is the first one that grows the buffer.

```c
for (i = 1; i <= num_iterations; i++) {
    mutate_buffer(mutated_buffer, mutated_buffer_size);
    if ((i % 500) == 0 && i != 0) {
        mutated_buffer_size = add_10_random_bytes(
            mutated_buffer, mutated_buffer_size);
    }
}
```

```c
int add_10_random_bytes(char *mutated_buffer, int mutated_buffer_size)
{
    int i;

    for (i = 0; i < 10; i++) {
        mutated_buffer[mutated_buffer_size + i] =
            (char)((rand() % 255) + 1);
    }
    return mutated_buffer_size + 10;
}
```

A seed of fixed length can reach a bug that depends on the early bytes. Extra bytes are how the same seed reaches a bug that depends on length. The added bytes are still values from 1 to 255. Growth adds length. It does not add a format.

## Standard output is the specimen

After the last iteration the buffer is written one byte at a time.

```c
for (i = 0; i < mutated_buffer_size; i++) {
    printf("%0c", mutated_buffer[i]);
}
```

`%c` prints one byte. The `0` in `%0c` does not change that. The loop writes the working length and then stops: no added newline, no count, no log line. The stream is usable as the next program's input because those extras are absent. Prints the author wanted while debugging are comments in this file.

## What this fuzzer can see

The run is repeatable, and it is blind. It does not record which path the next program took, so a change that nearly reaches a new branch is treated like any other change. It does not keep the strings the notebook found, so it has no preferred token. Bytes the target never reads are just as likely to be replaced as bytes the target compares.

That is a dumb mutator. The program is short because of it. The handout, the seed file, and the notebook's listing of the target stay off this page.
