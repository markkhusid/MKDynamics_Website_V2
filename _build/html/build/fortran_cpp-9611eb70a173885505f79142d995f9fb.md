# Fortran calling C++

Created with Grok Build

This program is the language boundary without a window. A Fortran `program` calls six C++ functions. The object-oriented part is small on purpose. There is no derived type. The thing to learn is how an argument crosses `bind(C)`, because the [particle viewer](cpp_fortran.md) uses the same mechanism in the other direction.

```{figure} images/fortran_cpp.png
:alt: Fortran main calling C++ functions
:align: center
:class: clickable-figure

The Fortran program calls the C++ functions. The arrays are 20 elements, and each sum is 85.
```

`iso_c_binding` gives Fortran names for C types: `c_int`, `c_float`, `c_double`. On this platform those are a 32-bit integer, a 32-bit real, and a 64-bit real. `bind(C, name="...")` sets the symbol the linker looks up. Without `bind(C)`, gfortran would publish a module procedure under a different name, and the C++ definition would not match it.

`extern "C"` on the C++ side turns off C++ name mangling, so the symbol really is `simple` and not an encoded C++ name. The header and the Fortran interface have to describe the same arguments. The compiler does not check one against the other. A mismatch is a wrong answer or a crash, not a compile error.

## `simple`

The Fortran interface has no arguments. The C++ function prints `Hello form C++`. That spelling is the string in `mycpp.cpp`. The call is `call simple()`, and it is the first line of the output.

## `easy`

Fortran passes two `integer(c_int)` arguments with the `value` attribute. `value` means the C function receives the integer itself, which is what a C parameter `int a` expects. Without `value`, Fortran would pass a pointer, and the C parameter would need to be `int*`.

`easy` prints `a = 2 b = 4`. The Fortran program does not print those integers again. The line in the output comes from `std::cout`.

## `no_problem`

Two inputs go across as `real(c_float), value`. The output is `real(c_float), intent(out)` with no `value`. On the C side that is `float* c`. Fortran's default for an argument is a pointer to the actual variable, and `intent(out)` documents that the subroutine writes it. C writes `*c = a + b`.

The call uses `c1`. C++ prints `a`, `b`, and `c = 6`. Fortran then prints `c1`, which is the same 6 in list-directed format, `6.00000000`.

## `no_problemas`

The Fortran interface is identical to `no_problem`. The C++ parameter is `float& c`, a reference. A C++ reference is still an address at the ABI level, so it matches the Fortran argument that was passed as a pointer. The body assigns `c = a + b` instead of `*c = a + b`. The output is a second copy of the same three lines, and Fortran prints `c2` as another `6.00000000`.

Those two 6s are `c1` and `c2`. They are not elements of the array that comes next.

## `many_numbers`

The Fortran interface describes three assumed-size arrays and a length. The C++ function takes `float* a`, `float* b`, `float* c`, and `int n`. Fortran passes the address of the first element of a contiguous array, which is what those pointers expect. `n` has `value`, so it arrives as an `int`.

```fortran
real(c_float) :: a(n)
real(c_float) :: b(n)
real(c_float) :: c(n)
integer(c_int), value :: n
```

`n` appears in the array bounds before it is declared. An interface body does not inherit `implicit none` from the host program, so the `n` in `a(n)` is an implicit integer as far as that specification is concerned. `gfortran -Wall` says that name may not be C-interoperable. The explicit `integer(c_int), value :: n` is still the dummy that gets passed. Declaring `n` first, and putting `implicit none` inside the interface, would clear the warning. The call with 20 elements still runs.

The program sets `a` to 42 and `b` to 43. The C++ loop writes `c[i] = a[i] + b[i]`. Fortran prints `c` from index 1 through 20. Every line is `85.0000000`. C++ does not print inside this function. All twenty lines are the Fortran loop.

## `myfunc`

This one is a function, not a subroutine. Both sides return `double`. Fortran uses `real(c_double)` for the result and `value` for the input, matching `double myfunc(double x)`. The C++ body returns `sin(x)`. The program prints `myfunc(1.0_c_double)`. The suffix `c_double` makes the literal a double. A bare `1.0` would be the default real, which on this compiler is still 32-bit, and the `value` dummy wants a double.

The printed value is `0.84147098480789650`, which is $\sin(1)$ for one radian.

`x` and `y` in the program are declared and never used. `-Wall` reports both. The call passes a literal, not `x`.

## CMake

```{literalinclude} code/fortran_cpp/CMakeLists.txt
:language: cmake
```

`LANGUAGES CXX Fortran` turns on both compilers. `GLOB` collects `main.f90` and, separately, `mycpp.cpp` and `mycpp.h`. Headers in an executable target are not compiled on their own. CMake lists them so the generated Makefile rebuilds when the header changes.

Configure finds `c++` and `gfortran`. The deprecation warning is the same `VERSION 3.5` warning as the other projects.

```{literalinclude} code/fortran_cpp/cmake_configure.log
:language: text
```

The build directory in that log is `/tmp/oop_learn/fortran_cpp/build`. The transcript drops that prefix and the `-I` flags. The real compile lines included the source directory and the build directory.

```{literalinclude} code/fortran_cpp/cmake_build.log
:language: text
```

The link line is the part to read slowly. The driver is `/usr/bin/c++`, not `gfortran`, because the program contains C++. CMake adds `-lgfortran -lquadmath` so the Fortran runtime is still there for the Fortran `program` statement, the `print` statements, and the array assignments. Linking the other way, with `gfortran` as the driver, would have needed `-lstdc++` instead.

Running `./fortran_cpp` produced the output above.
